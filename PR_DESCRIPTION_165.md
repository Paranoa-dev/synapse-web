feat(dev): add containerized local development environment

New contributors had to match CI's Node and npm versions by hand, and this
repository has already been bitten twice by not doing so: the lockfile was
regenerated to match one npm version (`910fd81`) and jsdom was downgraded for a
different Node (`91e5082`).

`docker compose up --build` now gives a dev environment pinned to exactly what
CI runs.

## One source of truth for the Node version

The issue asks for a single source of truth, and the starting point was worse
than none: `ci.yml` hardcoded `node-version: 20`, there was no `.nvmrc`, and no
`engines` field.

- **`.nvmrc`** (`20`) is now the only place the version is declared.
- **CI** reads it via `node-version-file: .nvmrc`, so it can no longer drift.
- **`Dockerfile.dev`** builds from the matching `node:` tag.

`scripts/toolchain-consistency.test.ts` (6 tests) enforces this mechanically, and
fails if they disagree or if `ci.yml` reverts to a hardcoded version. I verified
it actually catches drift: changing `.nvmrc` to `22` fails the
"Dockerfile.dev uses the same Node major" test, and reverting passes it again.
Without that check, a consistency test can silently stop testing anything.

npm is pinned **separately** via `ARG NPM_VERSION=10.8.2`, because the `node:20`
tag ships whatever npm was current when the image was built, and a lockfile
regenerated by a different npm causes noisy diffs and CI failures. The value
matches the commit that aligned the lockfile with CI.

## The settings that are easy to get wrong

Each of these is a fix for a specific silent failure, documented in place and in
`docs/local-development.md`:

- **Polled file watching** (`CHOKIDAR_USEPOLLING`). inotify events do not
  reliably cross a bind mount and not at all on Docker Desktop's virtiofs. The
  issue explicitly requires hot reload to work, and without polling it _silently_
  does nothing: the container runs, the page just never updates, and it reads as a
  broken setup. This is the one that would otherwise have looked "working".
- **Anonymous volumes for `node_modules` and `.next`.** A bind-mounted host
  `node_modules` shadows the container's, and native modules built for a different
  platform or libc fail in confusing ways.
- **Runs as the host UID/GID**, overridable via `HOST_UID`/`HOST_GID`, so files
  written into the bind mount are not root-owned.
- **Binds `0.0.0.0`.** Binding `localhost` inside the container is the classic
  reason a working container is unreachable from the browser.
- **`HUSKY=0`**, because `.git` is excluded from the context and there is no
  repository for husky to install hooks into.
- **Two-step dependency install** — `npm ci --ignore-scripts` for the cacheable
  layer, then `npm install` with scripts so native deps fetch their binaries.
  Those must not be skipped, or they break at runtime instead of at install time.
- **`.dockerignore`**, which did not exist. Without it a host `node_modules` is
  copied in, defeating the dependency layer cache. It also excludes `.env*`,
  since every variable there is `NEXT_PUBLIC_*` and ends up in the shipped
  bundle.

## Documentation

`docs/local-development.md` covers both setup paths, how to verify the container
matches CI, why each setting is needed, and troubleshooting for the five failure
modes above. The README's "Getting started" now offers both paths side by side.

## Not verified

**`docker compose up` was not run, because Docker is not available in this
environment** (`docker --version` → not found). The issue's DoD is "verified on a
clean machine", and I have not met that. What I have done instead:

- Every file that can be validated without Docker has been: both YAML files
  parse, the Dockerfile's assumptions about the repo were checked by hand
  (`package.json`/`package-lock.json` exist for the `COPY`, the `dev` script
  matches `CMD ["npm", "run", "dev"]`, `HUSKY=0` addresses the `.git` exclusion),
  and `.dockerignore` covers the context.
- The image is pinned to the same Node the current `npm test` / `npm run build`
  were just run on (Node 20 in CI; the local toolchain here is Node 24, which is
  exactly the drift this issue exists to remove).

A maintainer with Docker should run `docker compose up --build` once and confirm
hot reload before merging. The troubleshooting section anticipates the failures I
expect, but an expectation is not a test.

## Note

`node_modules` and `.next` in the working tree are bind-mounted as anonymous
volumes, so the host's own `node_modules` is not used inside the container. If
you switch back and forth between native and container workflows, run
`docker compose down -v` when leaving the container, or the next native install
may fight the volume.
